### Guía Definitiva de Arquitectura y Buenas Prácticas en Django REST Framework (DRF) Como Arquitecto Senior, mi prioridad es la viabilidad técnica a largo plazo y la robustez operativa. Una API no es un simple puente a la base de datos; es un contrato de software que debe regirse por los principios de la **"Twelve-Factor App"** . Para escalar de diez usuarios a diez millones, cada decisión de diseño debe minimizar el acoplamiento y maximizar la observabilidad. \-------------------------------------------------------------------------------- \#\#\#\# 1\. Estructura de Archivos: El Cimiento de la Escalabilidad La organización del código es una decisión estratégica. Una estructura descuidada no solo ralentiza el *onboarding* , sino que crea "Mega-Apps" imposibles de migrar a microservicios en el futuro. \#\#\#\#\# Implementación del Directorio config/ Para evitar el anidamiento redundante y separar la configuración del dominio, el estándar profesional exige iniciar el proyecto con: django-admin startproject config . (el punto final es innegociable). Esta estructura mantiene manage.py en la raíz y centraliza el control en /config. \#\#\#\#\# División de Ajustes (Settings) y Parity Nunca utilice un único settings.py. La paridad entre entornos es crítica para evitar fallos en producción. Divida su configuración en un paquete: text config/settings/ ├── \_\_init\_\_.py ├── base.py \# Configuraciones comunes (Apps, Middleware) ├── local.py \# Desarrollo (DEBUG=True, Debug Toolbar) ├── production.py \# Seguridad estricta, Cache Redis, SSL └── test.py \# Base de datos en memoria, rapidez de ejecución  \#\#\#\#\# Modularización por Aplicaciones (Apps) Adopte el concepto de **Contextos Delimitados (Bounded Contexts)** . Las aplicaciones deben residir en un subdirectorio apps/ para mantener limpia la raíz. **Gotcha Crítico:** Al mover una app a apps/, debe actualizar su apps.py para reflejar el path completo (name \= 'apps.mi\_app') y definir un label único. De lo contrario, el registro de Django fallará. \-------------------------------------------------------------------------------- \#\#\#\# 2\. La Capa de Servicios y Selectores: Separación de Responsabilidades El mayor error en Django es permitir "vistas gordas" ( *fat views* ). La lógica de negocio no debe depender del ciclo de petición HTTP. Si su lógica vive en la vista, no podrá ser reutilizada por una tarea de **Celery** o un comando de gestión sin duplicaciones peligrosas. \#\#\#\#\# Service Layer (Escritura) y Selector Layer (Lectura) Siguiendo el estilo de **HackSoft** , desacoplamos las operaciones: \* **services.py** **:** Centraliza la lógica de escritura. Debe ser agnóstica a la procedencia de los datos (API, Form, CLI). Use operaciones atómicas para garantizar la integridad. \* **selectors.py** **:** Centraliza las consultas. Localizar aquí las optimizaciones (como select\_related) evita que estas se dispersen por los serializadores, facilitando el mantenimiento. \#\#\#\#\# Comparativa: Modelos vs. Servicios | Responsabilidad | Modelos (models.py) | Servicios (services.py) | | \------ | \------ | \------ | | **Definición de Datos** | Define esquema y almacenamiento | Estructura agnóstica | | **Lógica de Negocio** | Prohibido (solo lógica de campo) | **Propietario único** | | **Reutilización** | Acoplado al ORM | Independiente del contexto (Celery/API) | | **Integraciones** | No permitidas | APIs externas, Notificaciones, etc. | \-------------------------------------------------------------------------------- \#\#\#\# 3\. Seguridad Avanzada y Protección de Datos La seguridad no es un "set and forget"; es un proceso de mitigación continua. \#\#\#\#\# Autenticación JWT y Clientes Múltiples \* **SPAs:** Almacene tokens en **HttpOnly Cookies** para neutralizar ataques XSS. \* **Mobile:** Utilice **Secure Storage** o Keychain. \* **Token Rotation:** Es obligatorio invalidar el *refresh token* tras cada uso. Esto limita la ventana de oportunidad tras un robo de credenciales. \#\#\#\#\# Prevención de "Mass Assignment" Evite el riesgo de que un atacante escale privilegios enviando campos no previstos (ej. is\_admin: true). \* **Solution 1 (Explicit Whitelisting):** Defina estrictamente los campos en sus Serializadores. \* **Senior Approach:** Utilice **DTOs (Data Transfer Objects)** o esquemas Pydantic para validar datos antes de que lleguen al servicio. \#\#\#\#\# Throttling y NUM\_PROXIES El rate limiting protege contra el abuso y asegura la disponibilidad (HTTP 429). **Advertencia Arquitectónica:** Si su API corre tras un balanceador o proxy (Nginx, Gunicorn), debe configurar NUM\_PROXIES en settings. Sin esto, el sistema identificará erróneamente la IP del proxy como el cliente, bloqueando a todos los usuarios legítimos o permitiendo ataques masivos. | Clase | Tasa Sugerida | HTTP Code / Header | | \------ | \------ | \------ | | AnonRateThrottle | 100/day | 429 Too Many Requests | | UserRateThrottle | 1000/hour | Retry-After: | \-------------------------------------------------------------------------------- \#\#\#\# 4\. Optimización del Rendimiento: Profiling vs. Guessing **"Optimizar sin perfilar es adivinar".** Antes de aplicar cualquier cambio, es imperativo usar **Django Debug Toolbar** o el logging de queries SQL para identificar el cuello de botella real. \#\#\#\#\# Resolución de N+1 y Caching \* **N+1:** Use select\_related para ForeignKeys (JOIN SQL) y prefetch\_related para Many-to-Many (consultas separadas unidas en Python). \* **Redis:** Es la opción obligatoria para producción. A diferencia de LocMemCache, Redis garantiza la persistencia del caché y los contadores de throttling en despliegues con múltiples servidores (escalado horizontal). \#\#\#\#\# Paginación Obligatoria Nunca exponga un endpoint de lista sin paginación. Los datasets grandes agotan la memoria del servidor y degradan la experiencia del usuario. Use CursorPagination para datasets masivos por su eficiencia en el escaneo de índices. \-------------------------------------------------------------------------------- \#\#\#\# 5\. Gestión de Errores y Documentación OpenAPI Una API consistente reduce el coste de integración de los clientes. \#\#\#\#\# API Versioning Sea dueño de sus cambios. Implemente versionado desde el día uno (preferiblemente basado en URL: /api/v1/). Es la única forma de iterar sin romper los flujos de ingresos de sus socios. \#\#\#\#\# Estandarización de Errores JSON Sus respuestas de error deben seguir un esquema predecible: json { "code": "validation\_error", "message": "Los datos proporcionados son inválidos.", "errors": { "email": \["Formato incorrecto"\] } }  \#\#\#\#\# Documentación con OpenAPI 3.0/3.1 Utilice drf-spectacular. Es la solución estándar que soporta las últimas versiones de OpenAPI, a diferencia de herramientas deprecadas. Use @extend\_schema para documentar comportamientos complejos y facilitar la generación automática de clientes para el frontend. \-------------------------------------------------------------------------------- \#\#\#\# 6\. Pruebas de Calidad con Pytest Pytest es superior al unittest tradicional por su mínima verbosidad y potencia funcional. \#\#\#\#\# Configuración y Fixtures Configure su entorno en pytest.ini: ini \[pytest\] DJANGO\_SETTINGS\_MODULE \= config.settings.test python\_files \= tests.py test\_\*.py  Utilice conftest.py para crear **fixtures modulares** (usuarios, clientes autenticados) que se compartan en todo el ecosistema de apps/. \#\#\#\#\# Parametrización y Base de Datos Reduzca el código duplicado con @pytest.mark.parametrize para probar múltiples roles o idiomas con un solo test. El marcador @pytest.mark.django\_db garantiza transacciones aisladas que se revierten automáticamente, manteniendo la integridad del entorno de pruebas. \-------------------------------------------------------------------------------- \#\#\#\# Resumen de Mejores Prácticas (Top 5\) 1\. **Defina un Modelo de Usuario Personalizado:** Hágalo antes de la primera migración. Ignorar esto obliga a realizar una "cirugía de SQL puro" extremadamente costosa en el futuro. 2\. **Lógica de Negocio en Servicios:** Mantenga las vistas por debajo de las 15 líneas; la vista solo coordina, no ejecuta. 3\. **Profiling Obligatorio:** No optimice por intuición. Mida queries y latencia (p95/p99) antes de tocar el código. 4\. **Trate la API como un Producto:** Establezca dueños, roadmaps, SLAs y documentación OpenAPI impecable. 5\. **Seguridad Proactiva:** Implemente rotación de tokens y whitelisting estricto (Mass Assignment) desde el diseño inicial.
